Engineering Playbook

Last updated: 2026-05-29

This playbook is a reusable operating manual for building production-grade MERN products with mobile support. It is written for projects that use:

  • MongoDB as the primary database
  • Node.js and Express as the backend API layer
  • React for web clients
  • React Native or Expo for mobile clients
  • TypeScript across the stack wherever possible

The goal is simple: every product should become operational, testable, secure, observable, and maintainable before real users depend on it.

This is not only a coding checklist. It is the product engineering system: what to decide, what to document, what to test, what to monitor, and what to refuse until the product is ready.

1. Core Doctrine

Every serious product must be built around these rules:

  • The frontend is not the source of truth.
  • The API owns validation, authorization, and business rules.
  • The database stores durable facts, not temporary UI assumptions.
  • Every external provider is behind an adapter.
  • Every production action must be observable.
  • Every risky action must be idempotent or safely retryable.
  • Every user-facing flow must handle loading, empty, error, and retry states.
  • Every secret must live outside source code.
  • Every deploy must be reversible.
  • Every incident must improve the system.

The fastest product is not the one built with the fewest checks. It is the one that does not collapse under its first real users.

Minimum documents before production:

  • Product brief: what problem is being solved and for whom.
  • Architecture overview: frontend, backend, database, provider dependencies.
  • API contract: routes, payloads, response shapes, auth requirements.
  • Data model: collections, indexes, relationships, retention policy.
  • Security sweep: OWASP-style review of auth, input, secrets, files, logs, rate limits.
  • Operational runbook: how to start, deploy, debug, rollback, and respond to incidents.
  • Current precedence list: what blocks launch, what is non-blocking, what is future work.

Documentation rule:

If a future engineer cannot understand the system from docs/, the product is under-documented.

3. Product Lifecycle Gates

Every feature moves through these gates:

flowchart LR

  Discovery --> Foundation --> Build --> Hardening --> Launch --> Operate

Phase 0: Discovery

Goal: decide whether the feature should exist.

Checklist:

  • Problem statement written in one sentence.
  • Primary user identified.
  • Existing workaround understood.
  • Success metric defined.
  • Legal, compliance, security, and cost risks listed.
  • Build, buy, or skip decision made.
  • Non-goals documented.

Gate 0:

  • Problem is real.
  • User is specific.
  • Success metric is measurable.
  • Scope can ship without becoming a second product.

Phase 1: Foundation

Goal: de-risk the architecture before coding deeply.

Checklist:

  • API contract drafted.
  • MongoDB collections and indexes designed.
  • Auth and authorization matrix written.
  • External providers identified.
  • Failure modes listed.
  • Idempotency and retry strategy defined for risky actions.
  • Test plan written.
  • Rollback strategy written.

Gate 1:

  • Another engineer can explain the design from the documents.
  • Major failure modes are known.
  • No unknown legal or security blocker is being ignored.

Phase 2: Build

Goal: build a correct feature behind a flag or internal access.

Checklist:

  • Backend route and service implemented.
  • MongoDB schema/index migration implemented.
  • Web UI implemented.
  • Mobile UI implemented if the feature is mobile-facing.
  • Loading, empty, error, and success states implemented.
  • Unit and integration tests added.
  • API contract updated.
  • Environment variables documented.

Gate 2:

  • Typecheck passes.
  • Lint passes.
  • Tests pass.
  • Feature is internally usable.
  • No known critical bug remains.

Phase 3: Hardening

Goal: make the feature production-ready.

Checklist:

  • OWASP API and mobile checks completed.
  • Route guard audit completed.
  • Rate limits configured.
  • Logs redacted.
  • Sentry or equivalent monitoring configured.
  • Health/readiness endpoints verified.
  • Dependency audit reviewed.
  • Load or stress test completed for the critical path.
  • Rollback tested.

Gate 3:

  • Security has no unresolved P0/P1 issue.
  • Observability is live.
  • Deployment path is tested.
  • Support and incident runbooks exist.

Phase 4: Launch

Goal: release without gambling.

Checklist:

  • Release notes written.
  • Feature flag or staged rollout plan ready.
  • Support notes ready.
  • Monitoring dashboard watched during rollout.
  • Rollback owner assigned.

Gate 4:

  • Internal test passes.
  • Staging test passes.
  • Production smoke passes.
  • Rollback command is known and tested.

Phase 5: Operate

Goal: keep the feature healthy or remove it.

Checklist:

  • Error budget defined.
  • Incidents reviewed.
  • Dependencies updated.
  • Metrics reviewed monthly.
  • Dead or unused paths removed.

4. Target MERN Architecture

The default shape:

flowchart LR

  Web[React Web] --> API[Node.js / Express API]

  Mobile[React Native App] --> API

  API --> Mongo[(MongoDB)]

  API --> Cache[(Redis Optional)]

  API --> Provider[Provider Adapter]

  Provider --> External[Payment / Email / Storage / KYC / Maps]

  API --> Jobs[Background Jobs]

  Jobs --> Mongo

  API --> Obs[Sentry / Logs / Metrics]

Recommended repo shape:

project/

  apps/

    web/

    mobile/

    api/

  packages/

    shared/

      src/types/

      src/schemas/

      src/constants/

  docs/

  scripts/

If using separate repos, keep the same logical boundaries.

Layer rule:

  • Web and mobile present the product.
  • API validates, authorizes, and orchestrates.
  • Services hold business behavior.
  • Repositories own database access.
  • Adapters own provider integration.
  • Jobs handle async work.
  • Shared packages may contain types and schemas, but not secrets or server-only authority.

5. Backend Rules: Node And Express

Route Handlers

Express route handlers must be thin.

Allowed:

  • route binding,
  • auth middleware,
  • request validation,
  • extracting params/body/query,
  • calling one service method,
  • returning the service response.

Forbidden:

  • provider API calls,
  • raw database logic,
  • business-rule branching,
  • fee or money math,
  • long async workflows,
  • direct file processing,
  • complicated authorization decisions.

Pattern:

router.post(

  "/orders/:id/confirm",

  requireAuth,

  validateBody(confirmOrderSchema),

  asyncHandler(async (req, res) => {

    const result = await orderService.confirmOrder({

      orderId: req.params.id,

      userId: req.user.id,

      idempotencyKey: req.header("Idempotency-Key"),

    });

    res.status(200).json(result);

  }),

);

Services

Services may:

  • load records,
  • enforce business rules,
  • call repositories,
  • call provider adapters,
  • emit domain events,
  • schedule jobs,
  • return typed errors.

Services must not:

  • trust client-computed state,
  • use unvalidated input,
  • swallow provider failures,
  • hide authorization failures as success,
  • mutate many resources without a transaction or compensating workflow.

Error Handling

Use a central error handler.

Every API error should map to a stable shape:

{

  "code": "ORDER_NOT_FOUND",

  "message": "Order not found.",

  "requestId": "req_123"

}

Do not leak:

  • stack traces,
  • database errors,
  • provider secrets,
  • JWTs,
  • OTPs,
  • raw webhook signatures.

Background Jobs

Use a queue when work is slow, retryable, or provider-dependent.

Common choices:

  • BullMQ with Redis
  • Agenda with MongoDB
  • provider-specific scheduled webhooks plus reconciliation jobs

Job rules:

  • jobs must be idempotent,
  • jobs must have retry limits,
  • jobs must log correlation IDs,
  • jobs must not assume previous attempts failed cleanly.

6. Database Rules: MongoDB

MongoDB is flexible, not lawless. Treat schema design as seriously as SQL schema design.

Collection Design

Each collection must document:

  • purpose,
  • owner service,
  • required fields,
  • indexes,
  • retention policy,
  • sensitive fields,
  • soft-delete behavior if any.

Use Mongoose, Zod, or another schema layer to validate shape.

Indexes

Indexes are production features.

Required index examples:

  • unique user email,
  • provider reference,
  • idempotency key plus user/action,
  • status plus due date for jobs,
  • createdAt for pagination,
  • foreign references used in lookups.

Every query used by a frequent endpoint or job must be backed by an index.

Transactions

Use MongoDB transactions when one business action must update multiple documents atomically.

Examples:

  • create order plus payment intent,
  • mark payout complete plus append ledger record,
  • accept invitation plus create membership,
  • revoke session plus append audit record.

If transactions are unavailable, design an explicit state machine and reconciliation job.

Money

Never store money as JavaScript floating point for arithmetic.

Use:

  • integer minor units, such as kobo/cents,
  • or Decimal128 with strict conversion rules.

Document currency on every money field.

Pagination

Avoid unbounded find() calls.

Use:

  • cursor pagination for feeds and histories,
  • limit plus sort,
  • stable indexes.

7. Web Rules: React

React web should be feature-based.

Recommended structure:

src/

  app/

  features/

    auth/

      api/

      components/

      screens/

      hooks/

      types.ts

    orders/

      api/

      components/

      screens/

      hooks/

      types.ts

  components/

    ui/

  lib/

  utils/

State Rules

Use server-state tools for server truth:

  • RTK Query,
  • TanStack Query,
  • Apollo if GraphQL.

Use local state for:

  • form input,
  • modal state,
  • active tabs,
  • temporary UI selection.

Do not store server lifecycle truth in Redux or Context unless it is a cached copy managed by a query library.

Forms

Forms should use:

  • schema validation,
  • clear field errors,
  • disabled duplicate submit,
  • server error mapping,
  • optimistic UI only when rollback is safe.

UI Requirements

Every screen must handle:

  • loading state,
  • empty state,
  • error state,
  • retry action,
  • success state,
  • permission-denied state where relevant.

8. Mobile Rules: React Native And Expo

Mobile development is not just React with smaller screens. It has its own release, security, storage, and device-state realities.

Recommended Setup

Use Expo for speed unless the product needs native modules Expo cannot support.

Allowed paths:

  • Expo Go for early UI exploration only.
  • Expo Development Build for realistic device testing.
  • EAS Build for installable Android/iOS builds.
  • Bare React Native only when native control is required.

Production mobile behavior must be tested in a development build or real release build, not only Expo Go.

Mobile Folder Shape

mobile/

  app/

  features/

    auth/

    profile/

    orders/

  components/

    ui/

  hooks/

  lib/

  navigation/

  storage/

  utils/

Secure Storage

Use secure storage for sensitive values:

  • Expo SecureStore,
  • iOS Keychain,
  • Android Keystore-backed storage where available,
  • native modules for non-exportable signing keys if AppSec-grade device binding is required.

Important distinction:

SecureStore can protect stored secrets, but it does not automatically mean the app has hardware-backed non-exportable request signing. If the product requires true device binding, use a native signing path where the private key cannot be exported and app code can only request signatures.

Mobile Authentication

Mobile auth must handle:

  • fresh install,
  • app update,
  • token expiry,
  • refresh failure,
  • revoked session,
  • lost device,
  • new device verification,
  • biometric opt-in if used,
  • offline mode if supported.

Deep Links

Every deep link must be treated as untrusted input.

Rules:

  • validate route params on arrival,
  • fetch server state before showing sensitive data,
  • do not trust amounts, roles, invite state, or provider status from link params,
  • preserve pending navigation only after login/device verification succeeds.

Push Notifications

Push tokens are not identity.

Rules:

  • bind push token to authenticated user session,
  • support token rotation,
  • unregister token on logout,
  • never put secrets or sensitive personal data in notification text.

Mobile Release Checklist

  • App version and build number incremented.
  • API base URL correct for environment.
  • Deep links tested on device.
  • Push notifications tested if used.
  • Login/logout/refresh tested.
  • Network loss and retry tested.
  • Error monitoring verified.
  • Android release build tested.
  • iOS release build tested if shipping iOS.

9. API And Type Contract Rules

The API contract is the bridge between backend, web, and mobile.

Use one of:

  • OpenAPI,
  • shared Zod schemas,
  • tRPC,
  • GraphQL schema,
  • generated TypeScript SDK.

Rules:

  • request and response shapes must be explicit,
  • enums must be shared or generated,
  • error codes must be documented,
  • breaking changes require versioning or coordinated rollout,
  • mobile clients need backward-compatible APIs because old app versions live longer than web deployments.

For every endpoint document:

  • method and path,
  • auth requirement,
  • request body,
  • query params,
  • response shape,
  • error codes,
  • idempotency behavior,
  • rate limit behavior.

10. Authentication And Authorization

Authentication proves who the user is. Authorization decides what they may do.

Do not mix them.

Auth Baseline

Support:

  • password auth or SSO,
  • refresh token rotation,
  • session revocation,
  • email verification if required,
  • password reset with hashed reset tokens,
  • rate-limited login and reset attempts,
  • device/session listing if the product is sensitive.

Authorization Matrix

Every project needs an authz table:

Actor

Every route should be tested for:

  • unauthenticated request,
  • wrong user,
  • wrong role,
  • revoked/suspended user,
  • valid user with invalid resource ownership.

11. Security Baseline

Use OWASP API Security, OWASP Top 10, and OWASP Mobile guidance as the baseline.

Backend Security

  • Validate all input server-side.
  • Use parameterized queries or safe ORM APIs.
  • Protect against NoSQL injection.
  • Rate limit auth and high-cost endpoints.
  • Use Helmet or equivalent security headers.
  • Configure CORS intentionally.
  • Keep secrets out of logs.
  • Hash passwords with Argon2 or bcrypt.
  • Store OTPs and reset tokens hashed.
  • Never return different login errors that reveal whether an account exists.
  • Verify webhook signatures using raw request body where the provider requires it.
  • Deduplicate webhooks.
  • Make financial or state-changing commands idempotent.

Web Security

  • Avoid unsafe HTML rendering.
  • Use a Content Security Policy where possible.
  • Keep tokens out of localStorage if cookie/session architecture is available.
  • Protect cookie sessions with HttpOnly, Secure, SameSite.
  • Validate all route params before fetching sensitive data.

Mobile Security

  • Do not log tokens, OTPs, or provider payload secrets.
  • Store secrets in secure storage.
  • Treat rooted/jailbroken detection as a signal, not a perfect guarantee.
  • Validate TLS and API host configuration.
  • Use native non-exportable keys for high-assurance device binding.
  • Avoid embedding long-lived provider secrets in the app.

File Upload Security

If users upload files:

  • size-limit uploads,
  • allowlist MIME types,
  • store outside the app server,
  • scan files before public access,
  • generate signed URLs,
  • strip or ignore dangerous metadata where relevant,
  • keep immutable file metadata records.

13. Observability And Operations

If you cannot see the system, you cannot operate it.

Logging

Use structured logs.

Every request should have:

  • request ID,
  • user ID if authenticated,
  • route,
  • status,
  • duration,
  • error code if failed.

Never log:

  • passwords,
  • OTPs,
  • access tokens,
  • refresh tokens,
  • private keys,
  • full payment payloads,
  • provider secrets.

Error Monitoring

Use Sentry or equivalent for:

  • server errors,
  • web errors,
  • mobile crashes,
  • release tracking,
  • environment separation.

Set release values from deployed commit SHA where possible.

Health Checks

Expose:

  • liveness endpoint,
  • readiness endpoint,
  • dependency checks for database/cache where appropriate.

Example:

GET /health/live

GET /health/ready

Readiness should fail if the app cannot safely handle traffic.

Metrics

Track:

  • request rate,
  • error rate,
  • p95 and p99 latency,
  • database latency,
  • queue depth,
  • job failures,
  • provider failure rate,
  • auth failure spikes.

14. CI/CD And Release Gates

Every pull request should run:

  • install with lockfile,
  • typecheck,
  • lint,
  • unit tests,
  • integration tests where practical,
  • build,
  • dependency audit or security scan,
  • formatting check.

Recommended commands:

npm ci

npm run typecheck

npm run lint

npm test

npm run build

npm audit --omit=dev

For monorepos, run per app:

npm --workspace apps/api run build

npm --workspace apps/web run build

npm --workspace apps/mobile run typecheck

Release rules:

  • no deploy from dirty worktree,
  • migrations reviewed before deploy,
  • environment variables present before startup,
  • rollback path known,
  • release notes written,
  • production smoke test executed.

15. Performance And Scalability

Before production:

  • check slow Mongo queries,
  • add missing indexes,
  • avoid unbounded pagination,
  • avoid N+1 provider/database calls,
  • cache stable expensive reads,
  • put external calls behind timeouts,
  • rate limit expensive endpoints,
  • queue slow work,
  • compress large responses,
  • keep frontend bundle size reasonable,
  • test mobile screens on low-end devices if target users use them.

Performance target should be written per product.

Default API target:

  • p95 below 500ms for simple reads,
  • p95 below 1s for complex reads,
  • no unbounded memory growth,
  • graceful failure when providers are down.

16. Runbooks

Every production project needs runbooks for common failures.

Database Down

Detection:

  • readiness fails,
  • API error rate spikes,
  • database connection errors.

Response:

  1. Confirm database provider status.
  2. Check connection string and network access.
  3. Pause background jobs if they increase load.
  4. Restore service or fail over.
  5. Run post-incident review.

Provider Down

Detection:

  • provider error rate spikes,
  • webhook delay,
  • timeout increase,
  • queue backlog.

Response:

  1. Stop marking provider-dependent actions as complete.
  2. Queue retryable work.
  3. Notify users with a delayed-processing message.
  4. Reconcile when provider recovers.

Secret Exposure

Response:

  1. Revoke exposed secret immediately.
  2. Rotate dependent secrets.
  3. Audit access logs.
  4. Invalidate affected sessions if needed.
  5. Add a prevention control.

Bad Deployment

Response:

  1. Roll back to last known good release.
  2. Disable feature flag if applicable.
  3. Check migrations and data writes.
  4. Confirm health and metrics.
  5. Write post-mortem if user impact occurred.

18. Provider Adapter Rules

External providers are replaceable infrastructure. They must never become the product's core business logic.

Provider examples:

  • payment processors,
  • bank rails,
  • KYC/KYB providers,
  • email/SMS providers,
  • file storage,
  • malware scanning,
  • maps/geocoding,
  • push notification services,
  • analytics tools.

Adapter rule:

Controller -> Service -> Provider Adapter -> External Provider

Never do this:

Controller -> Provider SDK

Frontend -> Provider secret

Database -> Provider-specific state as business truth

Every provider adapter must define:

  • provider name,
  • supported capabilities,
  • request shape,
  • normalized response shape,
  • provider reference fields,
  • timeout behavior,
  • retry behavior,
  • idempotency behavior,
  • webhook event mapping,
  • failure categories,
  • sandbox/live configuration.

Provider-specific fields can be stored for audit and reconciliation, but they should not leak into product state names unless the product itself truly depends on that provider.

Good normalized response:

type PayoutResult = {

  provider: "monnify" | "paystack" | "stripe";

  providerReference: string;

  status: "PENDING" | "SUCCEEDED" | "FAILED";

  rawStatus: string;

};

Bad normalized response:

type PayoutResult = {

  monnifyTransferCode: string;

  monnifyStatus: string;

};

Provider onboarding checklist:

  • Sandbox credentials available.
  • Live credentials unavailable to local development by default.
  • API base URL configurable.
  • Webhook secret configured.
  • Sandbox smoke script exists.
  • Provider docs saved or linked in docs/provider.
  • Adapter tests cover success, failure, timeout, duplicate, and invalid signature.
  • Provider outage runbook exists.
  • Fallback or manual operations path documented.

Provider decision record template:

19. Webhooks And Idempotency

Webhooks are not commands. They are provider claims that must be verified, deduplicated, normalized, and reconciled.

Webhook rules:

  • capture raw request body when signatures require it,
  • verify provider signature before processing,
  • reject stale timestamps if the provider supports timestamped signatures,
  • deduplicate by provider event ID or computed event hash,
  • acknowledge quickly,
  • process slow work asynchronously,
  • make processing idempotent,
  • never trust webhook payload alone for high-risk state if provider status APIs are available,
  • store raw payload safely for audit with secrets redacted where possible.

Webhook processing shape:

Receive -> Verify signature -> Deduplicate -> Normalize -> Claim event -> Process -> Record result

Webhook database fields:

  • provider,
  • event ID,
  • event type,
  • resource reference,
  • raw status,
  • normalized status,
  • received timestamp,
  • processed timestamp,
  • processing status,
  • failure reason,
  • payload hash.

Idempotency rule:

Any action that can move money, change ownership, send messages, start provider jobs, or create scarce resources must be idempotent.

Use idempotency for:

  • checkout/payment intent creation,
  • escrow/order creation,
  • payout/refund initiation,
  • file upload session creation,
  • KYC start session,
  • admin dispute resolution,
  • invitation acceptance,
  • password reset request if abuse-sensitive.

Store:

  • idempotency key,
  • actor ID,
  • action name,
  • request hash,
  • result status,
  • response snapshot if safe,
  • expiry.

Reject an idempotency key if:

  • the same key is reused by a different actor,
  • the same key is reused for a different action,
  • the request hash does not match the original request.

20. Identity, KYC, KYB, And Device Trust

Identity is not one thing. Keep these concepts separate:

  • authentication: who is logging in,
  • device trust: which device/session is acting,
  • KYC: whether a human has been verified,
  • KYB: whether a business has been verified,
  • authorization: what this actor may do now,
  • business state: whether the product action is allowed.

Never treat user.isVerified as universal authority for every financial action. Model verification states explicitly.

Recommended user verification states:

UNVERIFIED

PENDING

VERIFIED

REJECTED

EXPIRED

REVOKED

KYC provider rule:

KYC Provider -> Provider Adapter -> Internal KYC State -> Business Policy

The product should not let the provider become the business authority. The provider supplies evidence. The backend decides policy.

Device trust tiers:

  1. Soft device tracking

  • Device ID stored in secure storage.
  • Useful for UX and basic suspicious-login detection.
  • Not enough for high-assurance financial authorization.

  1. Software-backed request signing

  • Client signs request material using a generated key stored locally.
  • Useful for proving the end-to-end signing flow.
  • Still weaker if the key is exportable.

  1. Hardware-backed or native non-exportable signing

  • Private key is generated in iOS Keychain/Secure Enclave or Android Keystore where supported.
  • App code cannot export the raw private key.
  • App code can only ask the OS/hardware to sign.
  • This is the target for high-risk financial apps.

Sensitive routes should be able to require:

  • valid access token,
  • trusted device,
  • fresh challenge or nonce,
  • KYC/KYB state,
  • resource ownership,
  • business state.

Do not let SSO bypass device trust. Google, Apple, or enterprise SSO proves login identity. It does not prove the device is allowed to initiate risky actions.

Business KYB rules:

  • Business verification is separate from individual KYC.
  • A verified business does not remove the need to know the human operator.
  • Business owners or beneficial owners must be modeled explicitly.
  • Business verification should not silently convert into admin or financial authority.

21. Admin And Internal Operations

Admin panels are dangerous because they concentrate authority. Build them as internal operations tools, not casual dashboards.

Admin rules:

  • Admin auth is separate from user auth.
  • Admin identity provider should support MFA.
  • Admin roles must be explicit.
  • Admin actions must be audited.
  • Admins should not directly mutate money state.
  • Admins should request domain operations that the backend validates.
  • Sensitive admin actions should require fresh authorization.
  • Admin sessions should be shorter than normal user sessions.

Admin action record:

type AdminAuditRecord = {

  adminId: string;

  action: string;

  resourceType: string;

  resourceId: string;

  reason: string;

  before?: unknown;

  after?: unknown;

  requestId: string;

  ipAddress?: string;

  userAgent?: string;

  createdAt: string;

};

Admin dashboard minimum screens:

  • login/session status,
  • overview,
  • users,
  • KYC/KYB reviews,
  • disputes,
  • payments/payouts,
  • provider events/webhooks,
  • audit log,
  • system health,
  • settings/feature flags.

Admin route checklist:

  • MFA-capable auth provider.
  • Role guard.
  • Route-level permission check.
  • Audit event.
  • Rate limit.
  • No secrets in response.
  • No direct database mutation from frontend.
  • No direct provider action from frontend.

22. Environment Variables And Secret Hygiene

Environment variables are part of the system contract.

Every project needs:

  • .env.example with names and safe placeholder values,
  • environment validation at startup,
  • required/optional distinction,
  • strict mode for staging and production,
  • docs explaining where each secret comes from,
  • no real secret committed to git.

Environment groups:

APP_*

DATABASE_*

REDIS_*

AUTH_*

JWT_*

MAIL_*

STORAGE_*

PAYMENT_*

KYC_*

SENTRY_*

FEATURE_*

Startup should fail in strict environments when required secrets are missing.

Secret rules:

  • Never paste secrets into tickets, docs, or chat logs.
  • Never print full env values in smoke scripts.
  • Mask account numbers and references when possible.
  • Rotate secrets after accidental exposure.
  • Use separate sandbox, staging, and production credentials.
  • Use deployment secret stores, not committed .env files.

Production env checklist:

  • Database URL.
  • Redis URL if rate limits, queues, or nonces use Redis.
  • Auth/JWT secrets.
  • Mail/SMS credentials.
  • Provider API keys.
  • Webhook secrets.
  • Sentry DSN.
  • Sentry release from deployed commit SHA.
  • Public API/web URLs.
  • CORS allowed origins.
  • Strict mode enabled.

23. AI Agent Implementation Rules

When using an AI coding agent, give it constraints that protect codebase consistency.

Reusable prompt:

Modify this feature, but preserve codebase consistency.

Follow the existing architecture, naming conventions, folder structure,

state-management style, error handling, tests, and documentation patterns.

Do not introduce a new abstraction, dependency, or folder style unless the

existing codebase already supports it or the change clearly requires it.

Before editing, read the surrounding files and explain the implementation path.

After editing, run the relevant typecheck, lint, tests, and update docs/checklists.

Agent checklist before editing:

  • Read existing feature folder.
  • Read shared API/client/server patterns.
  • Identify source of truth for state.
  • Identify auth/guard requirements.
  • Identify tests that should be updated.
  • Identify docs/checklists that should be updated.

Agent checklist after editing:

  • No unrelated refactor.
  • No style drift.
  • No duplicated provider-specific logic.
  • No secret printed.
  • Tests run or limitation stated.
  • Docs updated if behavior changed.
  • Remaining blockers listed.

Do not ask an agent to "just make it work" for production features. Ask for:

  • correctness,
  • consistency,
  • tests,
  • operational safety,
  • documentation,
  • rollback awareness.

25. Definition Of Done

A feature is not done when the UI renders. It is done when it can be operated.

For a normal feature:

  • Product behavior is documented.
  • API contract is documented.
  • Backend validation exists.
  • Authorization is enforced.
  • Web/mobile UI handles loading, empty, error, retry, and success.
  • Tests cover happy path and important failures.
  • Logs and errors are observable.
  • Docs/checklists are updated.

For a provider-backed feature:

  • Adapter implemented.
  • Provider-specific code isolated.
  • Sandbox smoke works.
  • Webhook signature and dedupe tested.
  • Provider failure behavior documented.
  • Manual operations fallback exists if needed.

For a security-sensitive feature:

  • Threat model written.
  • Abuse cases listed.
  • Rate limit in place.
  • Secrets redacted.
  • Audit log exists.
  • Re-authentication or fresh challenge used where needed.
  • OWASP/API/mobile checks reviewed.

For a mobile feature:

  • Tested outside Expo Go when native behavior matters.
  • Deep links tested.
  • Offline/network-failure behavior tested.
  • Secure storage behavior reviewed.
  • App update/session recovery behavior understood.

Final Rule

If a product fails in production and this playbook did not help catch the failure earlier, update the playbook.
